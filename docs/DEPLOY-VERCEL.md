# Deploying on Vercel (phone-friendly)

Everything here can be done from a phone browser. Settings are gear icons; the ⋯ menu is the "more"
button on a deployment card.

## 1. One-time Supabase setup

1. supabase.com → **New project** (free tier is plenty).
2. **SQL Editor → New query** → paste all of `supabase/schema.sql` → **Run**.
   *Tip on a phone:* turn off autocorrect/keyboard substitutions first, or paste from a notes app that
   doesn't rewrite quotes.
3. **Authentication → Providers → Email** → turn **Confirm email** OFF.
   (Usernames map to `<username>@players.outrun.local`, so confirmation mail can never arrive.)
4. **Project Settings → API** → copy the **Project URL** and the **anon / publishable** key.
   The `service_role` key is refused by the game on purpose — it must never reach a browser.

## 2. Add the variables in Vercel

Project → **Settings → Environment Variables**:

| Key | Value |
| --- | --- |
| `SUPABASE_URL` | `https://xxxxxxxx.supabase.co` |
| `SUPABASE_ANON_KEY` | the long `eyJ…` anon key (or `sb_publishable_…`) |

Tick **Production** (and Preview/Development if you test on preview URLs) → **Save**.

The game also accepts `NEXT_PUBLIC_SUPABASE_URL`, `VITE_SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and
several other spellings — see `lib/supabase-env.mjs` for the full list. Nothing extra needs configuring if
the Supabase integration created them for you.

## 3. Redeploy — this is the step that gets missed

**Deployments** tab → newest deployment → **⋯** → **Redeploy**.

Environment variables are read when a deployment is built/started; an existing deployment keeps the old
environment forever.

## 4. Confirm it worked

In the build log you should see:

```
  supabase accounts: configured
    url: https://xxxxxxxx.supabase.co   (from SUPABASE_URL)
    key: SUPABASE_ANON_KEY (jwt, 219 chars)
```

If it says `NOT configured — the build runs in guest mode`, the log lists exactly which variable names it
looked for and what was missing.

In the game, tap **CONNECT SUPABASE** on the sign-in screen. The panel shows a live diagnostic:

- `VERCEL / SERVER ENV — URL ✓ · ANON KEY ✓` → the function sees your variables.
- `BUILD CONFIG.JSON ✓` → the static fallback baked at build time also has them.
- `✗` next to a value → that variable wasn't visible (typo, saved to the wrong environment, or no redeploy).

## 5. What is delivered, in order

| Order | Path | Notes |
| --- | --- | --- |
| 1 | `/api/config` | serverless function, reads env at request time, `no-store` |
| 2 | `/config.json` | generated by `npm run build`, `no-store` |
| 3 | `supabase-config.js` | inline script injected into the built HTML |
| 4 | `localStorage` | only for credentials pasted via **CONNECT SUPABASE** |

Only the anon/publishable key is ever shipped. A `service_role` JWT or `sb_secret_…` token is detected and
replaced with an error message instead of being served.

## 6. The realtime server (rooms of 1–8)

Vercel serves the front-end; `server.js` is the room host. Deploy it anywhere that keeps a process alive:
Render, Railway, Fly, a VPS, Docker — anything with a port. There are no build steps and no native modules.

```bash
npm install
npm start                 # node server.js — PORT || 3000, bound to 0.0.0.0
```

| Variable | Default | What it does |
| --- | --- | --- |
| `PORT` | `3000` | the port the host assigns; the server binds `0.0.0.0` so the platform can route to it |
| `ALLOWED_ORIGINS` | — | extra browser origins, comma separated: `https://*.vercel.app,https://play.example.com` |
| `PREVIEW_ORIGINS` | `1` | set to `0` to drop the coding-preview wildcard (`*.e2b.app`) from the allowlist |

`https://gemby-game.vercel.app` is allowed out of the box (plus `www`, `localhost` and `192.168.x.x` for
phone testing on your own Wi-Fi), so the Vercel front-end can open the socket without any configuration.
Check it from a phone: `https://your-server/health` lists the exact allowlist it is enforcing, and
`Access-Control-Allow-Origin` is echoed back only for origins on that list.

Point the deployed game at it in one of two ways:

* open the game with `?relay=https://your-server` (kept in the URL, so a shared link stays on that server), or
* set `window.__OUTRUN_RELAY__ = 'https://your-server'` in the deployment's own config.

Either way the client probes `/health`, sees `engine: "socket.io"`, and the HUD reads **SOCKET.IO**. If the
server is asleep or unreachable, the next lane (Supabase Realtime) takes over without an error screen.

## 7. Known limits on Vercel

* **No WebSockets** in serverless functions → online play uses Supabase Realtime directly, or the polling
  relay (`/api/room`) at roughly 3 updates/second when Supabase is not configured. Both are fine for a
  handful of friends; for 15 Hz rooms with up to eight players, run `server.js` as above.
* **Polling state is per lambda instance.** Two players may briefly sit on different warm instances; the
  client re-syncs as instances recycle. Same limitation as any stateless relay.
* **Free Supabase projects pause** after ~a week without traffic. Resume from the dashboard if the game
  suddenly reports network errors.
* **Env vars are build/runtime scoped.** Changing them requires a redeploy; changing `vercel.json` requires
  one too.
